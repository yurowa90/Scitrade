# 단계별 구현 계획

현재 상태는 `docs/STATUS.md`에 기록한다. 이 문서는 실행 순서와 완료 기준이며 출시 일정이나 구현 완료 보고가 아니다. 단계별 구현·검증 여부는 이 문서가 아니라 STATUS.md를 따른다.

## 공통 진행 방식

1. 현재 사용자 요청의 범위, `AGENTS.md`, 상태 문서와 기존 구현을 확인한다.
2. 해당 단계의 입력·상태 전이·사용자 행동·예상 결과를 작은 작업으로 나눈다.
3. UI와 독립된 경제 엔진에서 상태를 처리하고 최소 화면을 연결한다. 돈·재고·화물·채권·직원 예약의 소유자를 중복 만들지 않는다.
4. 실제로 구현한 범위에 맞는 검증을 실행한다. 데이터 검사 통과를 엔진 테스트 통과로 대신하지 않는다.
5. 완료 기준·검증 근거·남은 항목을 상태 문서에 기록한 뒤 다음 단위로 진행한다.

## M1 — 거래 한 건

**입력:** `data/scenarios.json`의 정상·선적 전 취소·지연 수락 사례, 매입·판매 견적, 직원·노선 데이터, `tests/acceptance_cases.json`. 항구 2곳·의류 1종·직원 1명·노선 1개로 시작한다. 시나리오별 명시값이 기본 설정보다 우선하며 목록을 합치지 않는다.

**의존:** M0 자료 검증. 착수 시 TypeScript 실행 환경과 UI 도구를 정하고 실제 버전·실행 명령을 기록한다. 캐릭터 이름·초상 연결 정보는 사용하되 성장·시너지 계산은 끈다. 미술 자산이 없으면 임시 표시임을 드러낸다.

**출력과 사용자 행동:** 견적 수락 → 매입 → 운송 예약 → 출발 → 인도 → 대금 회수의 상태 전이와 최소 거래 화면. 선적 전 취소 및 지연 수락 선택에 따라 현금·재고·채권·일정이 달라진다.

**완료 기준:** 세 경로의 결과가 각각의 fixture와 일치하고 중복 명령이 돈·재고·보상을 복제하지 않는다. USD 거래 장부와 KRW 급여를 섞지 않으며 인도·매출·채권·수금을 구분한다. 동일 상태·명령·시드로 결과를 재현한다. 실행한 엔진 테스트와 화면 확인 결과를 별도로 기록한다.

## M2a — 복수 거래와 직원·도시·문화

**입력:** M1 엔진, 직원·캐릭터 원안, 기본 성장 규칙, 도시 시설·접촉 인물·문화 활동 데이터, 해당 인수 명세.

**의존:** M1 완료. 복수 계약의 자금·직원·공간 예약을 한 체계에서 처리하고 저장 상태의 버전을 정한다.

**출력과 사용자 행동:** 복수 계약·운송 주선, 동료 6종의 발견·면담·영입·고용, 기본 배치, 업무 경험치·레벨·교육, 도시 방문·문화 활동, 저장·불러오기. 회사 보고서·직원 경험·인물 친밀·거래 신뢰를 구분해 보여준다.

**진행 순서 (작은 단위, 2026-10-04 제안, 2026-10-05 사용자 결정 반영):**
1. 복수 계약·운송 주선·자금·직원·선복 예약 — 전용 시나리오 `SCENARIO_M2_MULTI_TRADE`, 규칙 `M2a-rules-1`, 인수 명세 P0-M2A-01~03.
2. ✅ 동료 발견·면담·영입·고용 (TASK-0001 엔진·TASK-0002 화면, Codex 구현·Claude 검수, 2026-10-05 반영) — 기존 `SCENARIO_M2_MULTI_TRADE`에 후보 EMP03~06(만남 지역 모두 부산)을 붙인다. 현장 조사 1pt, 영입 의뢰 3pt, 계약금 후보 일급 5일분(DESIGN). 도감 발견과 고용을 분리하고, 의뢰·고용한 직원 시간을 같은 예약 체계에 넣는다. 영입하지 않는 경로의 검산 값은 그대로 둔다. 같은 단위에서 ‘한 번에 확정’을 첫 계약의 단계별 처리 뒤 공개하도록 바꾼다. 설계는 `docs/RESEARCH_APPLICATION.md`.
   - 2a. 사람 사용성 시험 — 처음 접하는 학습자 3~5명이 첫 계약과 영입을 진행한다. **빌드는 성장 화면 포함(2026-10-05 사용자 결정)이며 훈련·고용 선택 과제(T5)를 더했다. TASK-0005 반영 커밋으로 빌드를 고정했다(2026-10-06).** 진행 계획 초안: `docs/USABILITY_TEST_M2A.md`. 설계서 11절 목표(5명 중 4명이 도움 없이 첫 계약 종결)를 확인하고, 막힌 이유 문구와 한 번에 확정 공개 시점을 고친다. 연구로 발표할 경우 기관 승인과 보호자 동의를 먼저 받는다.
3. ✅ 업무 경험치·레벨·일반 훈련 (엔진 TASK-0004 Astra·반려 2회, 2026-10-05 반영 / 화면 TASK-0005 Sol·반려 1회 + 시험 준비 R2·R3, 2026-10-06 반영) — 직원별 완료 사건 ID로 한 번만 지급한다. 레벨·능력은 표시 전용이고 처리량 반영은 M2b(새 규칙 판본). 화면은 훈련 판단 지점에 ‘처리량은 그대로’를 밝힌다.
4. 도시 방문·문화 활동 — 위치·소요 시간·업무 공백을 같은 예약 체계로 검증한다. **2026-10-06 사용자 결정:** 본사 부산의 P0 활동 3종(CA01~03, 1일, 원화 비용)만 하고 출장은 없다. 경험치는 직원·활동별 첫 완료에만 10이다. 활동마다 4줄 기록(알게 된 점·범위·말하지 않는 것·아직 모르는 것)을 남긴다. 후속 견적은 다음 단위 M2a-4b로 미룬다. 구현은 TASK-0010(저장 판본 5 기반) → TASK-0011(엔진·자료) → TASK-0012(화면) 순서다. 결정·기본값은 `docs/DECISIONS.md` ‘M2a-4 도시 방문·문화 활동’.
4c. **평택 본사 전환 (2026-10-09 사용자 결정, TASK-0012 반영 뒤 시작)** — 한국 본사를 평택(평택·당진항)으로 옮기고 부산은 1장 환적 거점으로 남긴다. 항로·운송일수는 실제 평택 노선으로 다시 설계한다(M1·M2 기대값·사건·인수 명세 재계산). 순서: Claude 실제 운송일수 근거표·재설계안·평택판 문장 초안 → 사용자 승인 → Astra(자료·검사기·저장 판본·엔진 시험) → Sol(화면·기기 재측정) → Claude 검수. 사람 사용성 시험은 고정된 부산 3판으로 하고, 평택판은 새 주소로 낸다. 결정과 근거는 DECISIONS ‘평택 본사 전환’.
5. 창고 보관·처리 한도와 회사 고정비 — 출발항 화물의 무한 보관 가정을 없앤다. **같은 단위에서 결정적 견적 갱신과 지역 시세표를 만든다(2026-10-09 사용자 결정, 대항해시대 적용표 DK-01·06·28).** 지금은 견적 6건이 시작 때 한 번 생기고 3일에 모두 만료되어, 90일 중 교역이 첫 묶음으로 끝난다. 같은 시드·날짜면 같은 견적, 체결 계약 가격 고정, 작은 회사의 판매는 세계가격을 거의 바꾸지 않음, 지수와 실제 금액 구분, 관측 시각 표시를 완료 조건에 넣는다. 창고 판단(CL-03)은 거래가 반복될 때 의미가 있으므로 함께 검증한다.

**완료 기준:** 도감 발견이 고용을 자동 생성하지 않는다. 업무·교육·현지 활동의 시간과 비용이 충돌 없이 예약된다. 경험치와 문화 보상의 중복 처리를 막는다. 저장 전후 현금·진행 업무·위치·성장·관계 상태와 이후 결과를 재현한다. 캐릭터 계산은 전용 M2 시나리오에서 활성화하고 M1 검산은 유지한다.

## M2b — 강화·회사 조직·프로젝트 시너지

**입력:** M2a 인력·예약·성장 상태, `data/organization.json`, `data/job_templates.json`, `data/team_synergies.json`, 강화 규칙과 캐릭터 인수 명세.

**의존:** M2a 완료. 조직 소속, 편성안, 실제 업무 예약을 분리한다.

**출력과 사용자 행동:** 강화 +1~+3의 교육 투자, 부서·상설팀·역할 화면, 책임자 1명과 지원 최대 2명의 프로젝트 편성, 초기 시너지 2규칙. 아직 도입하지 않은 전문팀에는 조건과 도입 단계를 표시한다.

**완료 기준:** 강화의 비용·시간·레벨 조건·완료 보상을 한 번만 반영한다. 강화 중 다른 업무에 투입할 수 없다. 팀을 저장하는 것만으로 인력을 예약하거나 전사 이익을 늘리지 않는다. 시작 때 고정한 실제 참여자로 시너지를 계산하고 업무별 10% 상한 및 시설 잔여 처리량을 지킨다. 관세·계약 가격·선박 속도·물리적 적재 용량에는 성장 배율을 적용하지 않는다.

## 고전게임 인사이트를 기존 단계에 연결 (2026-10-08)

[CL-01~08 적용표](CLASSIC_GAME_INSIGHTS.md)는 기존 단계의 사용자 경험과 검증 기준을 보강한다. 별도 대형 기능 묶음이나 구현 완료 표시가 아니다.

| 기존 단계 | 연결할 기획·검증 기준 |
|---|---|
| 기존 M2a 보고·예약 화면의 후속 보강 | 거래 성과/운영 지출/현금 시점, 계획/실제 일정, 수요/용량/병목을 연결해서 설명한다(CL-01~03). 기존 단일 엔진 상태를 재사용한다. |

## 검증과 인계

- 현재 제공한 JSON 23개는 자료 검증 대상이며, 인수 명세 22개는 구현할 엔진의 기대 결과다. 게임 테스트 실행 결과가 아니다.
- 단계마다 관련 인수 명세를 실행 가능한 검증에 연결한다. 구체적인 위험이 남아 있을 때 검증을 추가하며, 미구현 기능의 통과 결과를 만들지 않는다.
- 두 AI는 `docs/STATUS.md`의 상태 갱신 규칙을 공동으로 따른다. 변경한 파일과 결정, 실제 검증, 다음의 작은 작업을 남긴다.
- 교육과정 후속 개정 대조와 성취기준 코드 매핑은 별도 검토 항목이다. 최신 교육과정 전체를 확인했다고 표시하기 전에 판본과 대조 범위를 기록한다.
- 실제 그림·애니메이션·경제 보정·교육 효과는 제작 또는 검증 결과가 생긴 뒤에만 완료로 기록한다.
