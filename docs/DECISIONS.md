# 구현 결정과 보류 항목

## 기본 방향

PC 브라우저·싱글플레이·1일 단위 시뮬레이션. 세계지도와 도시·본사 화면을 오가며 거래·직원·현지 활동을 조율한다. 처음에는 2D 지도와 입체 시점의 2D 사업장 표현을 사용하고, 실제 3D 자유 이동은 별도 규모 판단 뒤 결정한다.

## 단계의 경계

| 단계 | 산출물 | 통과 기준 |
|---|---|---|
| M0 | 명세·fixture·출처·상태표 | 이 자료의 미확정 값과 실제 값 구분, 거래 한 건 수동 검산 |
| M1 | 의류 한 건의 매입~회수 | 정상·지연·취소의 돈과 화물 정합성, 최소 화면 |
| M2 | 복수 계약·운송 주선·직원·저장, 도시·문화 원형 | 자금·업무·공간 경쟁, 관계 범위, 저장 후 재현 |
| M3 | 6거점·8품목·6사건·2경쟁사 | 정책 대상·발효일·공통 충격, 대체 대응 |
| M4 | 소량 실제 자료 수집 확대·모형 보정 | 가용성·단위·집계 수준·추정 범위·한계 기록 |
| M5 | 본사·도시 표현·이야기·90일 체험 | 거래·문화 활동의 의미를 설명할 수 있는 사용성 확인 |
| P1 | 타사 주식·기술 도입·문화 활동 확장 | 투자와 영업의 현금 공유, 가격·체결·평가 분리 |
| P2 | 투자 유치·자사 IPO·주주관계 | 신주와 구주·지분·자금·분배 정합성, 다년 성장 |

## 구현 전에 정할 항목

- UI 라이브러리·게임 렌더러의 실제 버전: 시제품 착수 때 호환성을 확인한다. 엔진은 TypeScript 독립 모듈을 기본 후보로 한다.
- 지도·사업장 그래픽의 제작 방식과 예산: 본 패키지는 에셋을 포함하지 않는다.
- 국가별 관세·HS·운송시간·가격: 현재는 fixture이며 실제 자료 묶음과 분리한다.
- 관계 점수·실력 성장 속도·주가 변동성: 아직 검증되지 않았다. 임의 값을 넣으면 DESIGN으로 기록한다.
- 직원 탐방이 없는 플레이에서도 핵심 정보는 유료 조사·외부 인력·보고로 얻을 수 있게 한다.
- IPO의 실제 국가별 규제 재현 수준과 세금: P2 시작 전에 별도 결정한다. 초기 가상 거래소 규칙을 현행 법으로 설명하지 않는다.

## 데이터 fixture의 선택

첫 거래는 부산→요코하마 의류 100개, 매입 1,000 USD·운임 200 USD·가상 관세 50 USD·판매 1,400 USD다. 직접 기여이익은 급여 전 150 USD다. 출발일2·도착일7·납기8·수금10으로 상태 차이를 드러낸다. 실제 노선의 운임·일정·관세를 뜻하지 않는다.

개별 검산 사례의 ‘100 단위 현금’ 예제는 위 월드 데이터와 별개의 회계 단위 없는 fixture다. 두 시나리오의 초기 상태를 합치지 않는다.

## 시나리오 초기화와 문화 보상

각 시나리오는 새 상태로 시작한다. 명시한 시나리오 설정이 기본값보다 우선하며 목록은 합치지 않고 교체한다. M1·M2는 P0 기능 단계, P1은 P1 단계로 변환하고 주식 활성 여부도 함께 적용한다. variant는 지정된 기본 시나리오를 읽은 뒤 자기 값으로 덮는다. 취소·지연 사례의 기대값은 USD 거래 장부이고 KRW 급여·고정비는 별도다.

문화 활동의 회사 보고서는 회사별 1회, 직접 경험은 직원별 1회, 친밀 관련 후속 기록은 직원과 인물 쌍별 1회 처리한다. 다른 직원의 첫 참여는 허용하며 경비·업무 시간은 새로 사용한다.

## v0.4 확정 방향과 설계 제안

사용자 확정 방향: 동물·영물·괴물·신수 직원 수집, 첨부 영상과 같은 밝고 귀여운 그래픽, 속성·덱 시너지·국가 요소, 직원 투자·레벨·강화, 회사 부서·팀·역할.

개발 제안: P0 6종/P1 추가6종, 3인 프로젝트팀, 6능력·6속성, 3부서·7팀, 레벨1~10, 강화+0~+3, 처리량 시너지 상한10%. 수치는 플레이테스트로 변경할 수 있다. 새로운 제안값을 사용자의 확정 숫자로 표현하지 않는다.

초기 단계를 M2a(영입·레벨·교육)와 M2b(강화·조직·시너지)로 나눈다. M1의 거래 검산은 유지하며 영상 스타일의 완성 아트와 홀로그램 애니메이션은 거래·직원 상태가 연결된 뒤 제작한다. 신규 인수 기준8개는 tests/character_acceptance_cases.json에 있다.

## M1 엔진 구현 결정 — 2026-10-04

기술 구성: TypeScript 7.0.2, Vite 8.3.2, Vitest 5.0.3 (`package-lock.json`으로 고정). 엔진은 `src/engine`, 데이터 변환은 `src/content/m1.ts`, 화면은 `src/ui`. 실행: `npm install` → `npm run dev`(화면), `npm test`(엔진 테스트).

장부와 상태:
- 통화별 복식 장부. USD 거래 장부와 KRW 급여 장부는 같은 구조이지만 합산하지 않는다. 금액은 정수 최소 단위(USD cents, KRW 원). 통화 없는 검산 사례는 ISO 4217의 `XXX`로 표시한다.
- 매입 대금은 견적 수락 때 현금 → 재고. 운임은 예약 때 현금 → 선급운임, 출항 때 선급운임 → 재고. 관세는 도착 때 현금 → 재고. 인도 때 재고 장부가액 전액을 매출원가로 대체하고 매출·채권을 인식한다. 결제일에 채권 → 현금.
- 관세 반올림: basis point 정수 계산, 최소 단위에서 0.5는 0에서 먼 쪽으로 올림.
- 현금이 부족한 필수 지급(관세·급여·보상)은 음수 현금 대신 미지급금(부채)으로 기록하고 다음 날부터 갚는다. 관세가 미지급이면 반출하지 않는다. 지급 불이행 유예기간은 미확정(`data/parameters.json`의 `PAR_PAYMENT_GRACE_DAYS` = null)이므로 경영 실패 판정은 구현하지 않았다.

하루 처리 순서 (DESIGN 7·9절의 표를 따름): ① 일자 시작·사건 공개(openDay) → 의사결정 정지 → ② 명령을 대기열 순서대로 검증·실행(앞 명령의 지출 반영) → ③ 직원 업무 진행 → ④ 출항·도착·통관 → ⑤ 인도·납기 판정 → ⑥ 수금 → 밀린 지급 → 급여 → ⑦ 견적 만료 → ⑧ 불변 조건 검사·마감. 같은 날 다시 열거나 이미 마감한 날을 다시 마감해도 아무 일도 일어나지 않는다.

데이터에 구조화 필드가 없어 엔진에서 정한 값 (모두 DESIGN). 사용자가 2026-10-04에 제안 내용을 확인하고 반영을 요청하여, `data/scenarios.json`의 `contract_terms`(기본 시나리오, 변형이 상속)와 `port_restriction`(지연 사례)으로 옮겼다. 엔진은 상수가 아닌 이 데이터를 읽고, `tools/validate_data.py`가 fixture 기대값과의 산술 일치를 검사한다:
- 수출 준비 업무량 2pt: EMP01의 하루 처리량과 같아 1일 배정 시 2일 출항 전에 끝난다.
- 출항 전 취소: 운임 150 환급·취소비 50·고객 보상 0·공급자 반품 없음 (SCENARIO_M1_CANCEL_PREDEPARTURE 문장). 준비 미완료로 출항편을 놓친 경우에도 같은 조건으로 예약을 정산한다(엔진 결정). 출항 후 취소는 M1에서 허용하지 않는다.
- 지연 사례: “공통 지연 1회, 정확히 2일”을 요코하마항 7~8일 하역 중단 사건 1개로 구현했다. 지연일을 미리 더하지 않고 실제 대기한 날만 누적하며, 공지일은 5일이다(엔진 결정).
- 납기 경과 인도: 사전 계약 조건의 50 USD 감액을 지연 일수와 무관한 1회 감액으로 정했다(`late_delivery.basis = flat_once_regardless_of_late_days`). 감액 후 금액을 매출·채권으로 인식하고 별도 비용으로 다시 빼지 않는다. 일수 비례 조항이 필요하면 새 basis 값을 추가하고 엔진·검증을 함께 바꾼다.
- 결제일: 시나리오의 `cash_payment_due_day`를 쓰되 인도일보다 이를 수 없다.
- 예약 마감: 출항 전날까지. 화물 공간은 g·L 정수로 비교한다.

화면: 대기 명령을 실행했다고 가정한 사본(`planState`)으로 ‘오늘 실행 예정’ 계약을 보여 주고, 현금·보고는 확정 상태만 쓴다. 지연 공지의 세 선택지 중 ‘현재 예약으로 대기’만 활성화하고 나머지는 이유와 도입 단계를 표시한다. 동료 카드는 사용자가 공유한 레퍼런스 화면(`references/user_character_screens.json`)의 구도만 참고한 자리표시자다. 한정 일련번호·판매·방생·전투 능력치는 제외하기로 하고 `docs/ART_DIRECTION.md`와 `docs/CHARACTERS_AND_ORGANIZATION.md`에 반영했다.

## 그림 제작과 세계지도 — 2026-10-04

- **그림 제작:** 사용자 결정으로 동료·배경 그림은 생성형 AI(미드저니 등)로 만든다. 사람 일러스트 외주는 쓰지 않는다. 일관성 유지 절차와 권리·공개 원칙은 `docs/art/PROMPTS.md`에 있다. 그림은 캐릭터·장면만 담고, 카드 테두리·아이콘·레벨은 코드가 그린다.
- **그림 등록:** `src/assets/manifest.json`의 `status: approved` 항목만 화면에 쓰고, 그림이 없는 동료는 자리표시자를 유지한다. 출처 기록(도구·버전·프롬프트·참조·작업 ID·사람이 고친 내용)을 필수로 한다.
- **세계지도:** 개념 도형 지도를 위성 합성 영상 기반 게임 지도로 바꿨다(`scripts/build_map.py`, `src/ui/map.ts`). `data/world.json`에 지도 표시용 근사 좌표 `geo_position`, `data/routes.json`의 ROUTE01에 표시용 항로 `map_waypoints`를 추가했다. 둘 다 거리·운송시간 계산에 쓰지 않으며 기존 개념 좌표 `map_position`은 유지한다.

## 동료 모티프: 실재 동물과 신화 속 존재만 — 2026-10-04

사용자 결정: 창작 결합 생물은 쓰지 않고 신화 속 동물·환수·신수·괴물을 쓴다. 창작 결합 생물 4종을 다음과 같이 바꿨다. 직원 ID·직무·속성·능력치·고유 특성·채용 조건은 그대로 두어 기존 검증과 시너지 규칙(물 속성 조합 등)을 유지한다.

| ID | 이전 | 변경 | 업무와의 연결 |
|---|---|---|---|
| EMP04 (P0, 물·운영) | 돌몽 (거북+멧돼지 창작) | 현돌 — 현무 | 북방·물의 신수, 칸이 나뉜 등껍질 = 적재 계획 |
| EMP06 (P0, 그림자·운영) | 밤꾸미 (나방형 창작) | 바름 — 해치 | 시비를 가리는 외뿔 짐승 = 서류 대조 |
| EMP10 (P1, 대지·운영) | 모래봉 (염소+모래언덕 창작) | 쇠꼬미 — 불가사리 | 쇠를 먹는 괴물 = 고장 난 장비 정비·재활용 |
| EMP12 (P1, 그림자·영업) | 묵구름 (고양이+구름 창작) | 두루 — 백택 | 모든 요괴를 아는 신수 = 소문의 출처 검증 |

출전 조사는 `data/characters.json`의 `myth_reference`(전승, 요약, 출처, 확인 수준, 디자인 주의)에 기록했다. 확인 수준은 백과사전·기관·언론·2차 자료의 개요이며 한문 원전 대조는 하지 않았다. 스키마의 `creature_kind`는 `animal`과 `myth_inspired`만 허용하고, `tools/validate_data.py`가 창작 결합 생물 금지와 직원·캐릭터 이름 일치를 검사한다. `docs/DESIGN_v0.4.md`는 판본 기록과 교육과정 해시 검증 대상이라 고치지 않았으며, 그 문서의 ‘돌몽’은 현재 ‘현돌’을 뜻한다.

## 국가별 동료 수집과 멸종위기종 — 2026-10-04

사용자 결정: 수집 게임 느낌을 강화하고, 6개 거점 국가마다 대표 동물·희귀 동물(멸종위기종 중심)·신화와 전설 속 존재를 동료로 만난다. 대항해시대처럼 동료 수를 늘린다.

- 동료를 12종에서 48종으로 늘렸다. 신규 36종(EMP13~EMP48)은 release_phase P1이며, 한국 동료는 M2a(부산), 다른 나라 동료는 그 도시 콘텐츠가 열리는 M3에서 만난다.
- 모든 동료에 `encounter`(만남 국가·도시·분류·해금 단계)를 추가했다. 기존 원칙(국적 없음, 국가 고정 능력 없음, 근무 지역 제한 없음)은 유지하고, ‘그 나라에서만 취업’ 금지 규칙을 ‘그 나라에서 처음 만남’으로 바꿨다.
- 실재 동물에 `conservation`(IUCN 등급, CITES 부속서, 국내 보호 지정, 출처, 확인 수준, 디자인 주의)을 기록했다. 위급(CR) 12종, 위기(EN) 9종, 취약(VU) 3종을 포함한다. 웹 2차 자료로 확인한 항목과 작성자 지식 기반 항목을 구분했다.
- 멸종위기종은 보전 협력 의뢰로만 합류하고 거래 상품·부산물로 등장시키지 않는다. 수집 보상은 비경제 보상으로 한정한다.
- 속성은 6종이 8명씩 고르게 나뉜다. 능력 합계 300·희귀도 배율 없음 규칙은 그대로다.
- `tools/validate_data.py`에 만남 국가·도시 일치, 실재 동물 보전 기록, 희귀 동물 비무작위 합류, 이름·특성 태그 중복 금지 검사를 추가했다.

비판적 검토: 동료가 많아지면 그림 제작량(카드·초상·동작)이 크게 늘고, 능력·특성이 비슷한 동료가 생기면 수집의 의미가 약해진다. 이를 막기 위해 동료마다 고유 업무 특성 태그를 다르게 두었고, 그림은 카드 1장을 먼저 만들고 동작 그림은 고용 가능한 동료부터 만드는 순서를 권한다.

설계 의도: 직접 무역 두 건은 합쳐 3,530이 필요해 3,000으로 동시에 할 수 없다(자금 선택). 운송 주선 두 건은 같은 출항편에 32m³로 30m³ 한도를 넘는다(선복 선택). 급한 가구를 다음 편으로 미루면 납기를 넘겨 감액된다. 기대 경로 두 개(화장품+주선 2건 = 기여 500, 의류+주선 2건 = 430)와 거절 사례 두 개를 `data/scenarios.json`의 `expected_paths_usd`·`expected_rejections`에, 인수 명세 P0-M2A-01~03을 `tests/acceptance_cases.json`에 두었다.

**규칙 판본:** 시나리오가 `engine_rules`로 규칙을 고른다. M1 시나리오는 `M1-rules-1`(지금 현금만 확인)을 그대로 쓰고, M2 시나리오는 `M2a-rules-1`을 쓴다. M1 검산 27개 테스트는 기대값을 바꾸지 않고 통과한다.

**자금 예약 (`COMMITTED_OUTLAYS`):**
- 체결한 계약이 앞으로 낼 돈을 예약으로 계산한다. 운송편을 아직 예약하지 않은 계약의 운임, 직접 무역의 아직 내지 않은 관세다. 매입대금은 수락 때 이미 냈으므로 넣지 않는다.
- 사용 가능 자금 = 현금 − 예약 − 미지급 의무. 새 계약은 매입+운임+관세(운송 주선은 운임)가 사용 가능 자금 이내일 때만 받는다. 운임을 낼 때는 그 계약 자신의 운임 예약을 빼고 계산한다.
- 예약은 상태에서 매번 계산하며 저장하지 않는다(`src/engine/reservations.ts`). 같은 돈을 장부와 예약표 두 곳에 기록하지 않기 위해서다.
- 출항을 놓쳐 예약이 풀리면 운임 예약이 다시 생긴다. 이때 사용 가능 자금이 음수가 될 수 있으며, 화면은 음수를 그대로 보여 준다.

**운송 주선 회계:**
- 고객 화물은 `owner: CUSTOMER`로 기록하고 장부가액 0으로 둔다. 회사 재고·자산·상품 매출에 들어가지 않는다. 신고가액은 설명용이다.
- 운임은 다음 순서로 옮긴다. 예약 때 현금 → 선급운임, 출항 때 선급운임 → 주선 진행원가(`FORWARDING_WIP`, 자산), 인도 때 주선 진행원가 → 주선 원가(`FORWARDING_COST`). 서비스 매출(`FORWARDING_REVENUE`)과 같은 날 비용이 된다(대응 원칙).
- 상품 매출(`REVENUE`)·매출원가와 주선 매출·주선 원가는 계정을 나눈다. 회사 보고서와 계약별 기여이익 모두에서 구분해 보여 준다.
- 운송 주선 화물의 관세는 수입자(고객)가 부담하는 것으로 단순화했다(`forwarding_duty_payer: consignee`). 실제로는 인코텀즈·통관 대행 계약에 따라 주선업자가 대납 후 청구할 수 있다. 이 경우 회사 현금 흐름이 달라지므로 M3 통상 단계에서 별도 계약 조건으로 다룬다.
- 출항 전 취소와 출항 불참 정산(운임 150 환급·취소비 50)은 M1과 같다. 고객 화물은 화주에게 돌려준다(`RETURNED_TO_OWNER`).
- 납기 경과 감액 50(1회)은 서비스 대금에도 같은 조건으로 적용한다.

**직원·선복:**
- 직원은 한 번에 업무 하나만 진행한다. 운송 주선 준비(화물 인수·선적 서류)는 2pt다. 처리량은 계속 LEGACY_FIXED다.
- 선복은 출항편마다 무게(g)·부피(L) 합계를 한도와 비교한다. 같은 날 대기 명령도 앞 명령의 예약을 반영해 누적 검증한다.
- 마감 불변 조건을 더했다. 출항편 한도 초과 금지, 직원별 진행 업무 1건, 고객 화물 장부가액 0, 주선 진행원가 = 운송 중인 고객 화물 운임 합계다.

**저장:** 저장 형식 판본 2. 운송 주선 계약의 `serviceOfferId`와 화물 소유자 `ownerPartyId`를 추가했다. 판본 1(M1) 저장은 `migrateV1toV2`가 새 필드를 ‘해당 없음’(null)으로 채워 명시적으로 이관하고 경제 값은 바꾸지 않는다. 규칙 판본이 다르면(M2 저장을 M1 규칙으로 읽기 등) 거절한다. 화면 저장 칸은 `scitrade-save`이고, 불러오기는 예전 칸 `scitrade-m1-save`도 읽는다.

**비판적 검토와 남은 한계:**
- 예약은 ‘확정된 지출’만 묶는다. 급여(KRW)·지연 감액·취소비처럼 일어날 수도 있는 지출은 예약하지 않는다. 그래서 사용 가능 자금은 안전 여유가 아니다. 위험 대비 예비자금 규칙은 지급 불이행 유예기간(`PAR_PAYMENT_GRACE_DAYS`)과 함께 정해야 한다.
- 운송 주선 서비스 대금을 건당 고정값으로 두었다. 실제 운임 견적은 부피·무게(운임톤)와 구간에 따라 달라진다. 운임표 모형은 M4 자료 보정에서 다룬다.
- 직원의 직무(영업·운영)는 아직 업무 배정에 영향을 주지 않는다. 직무 적합도와 처리량 차이는 캐릭터 계산을 켜는 M2a 이후 단계에서 다룬다.
- 창고(보관 한도·하루 처리 한도)와 회사 고정비는 이번 단계에 넣지 않았다. 현재 출발항 화물은 무한 보관으로 가정한다.

1. **시간 척도:** 상하이→로테르담은 수에즈 경유 약 27일, 희망봉 경유 약 35일이다. 90일 캠페인에서 유럽 왕복은 한 번이 빠듯하다. 실제 운송일수에 가깝게 두고 캠페인을 장(章) 구조(1장 동아시아 90일, 2장 원양)로 나누는 안을 제안했다. 시간 압축은 교육적 정확성을 해치므로 권하지 않는다.
2. **기존 노선 일수:** 부산→요코하마 5일은 실제 직항 약 3일보다 길다. M4 보정 때 실제값으로 맞추고, M1 검산 기대값도 그때 함께 갱신한다. *(2026-10-09 정정: 선사 요일표로 세면 부산→요코하마는 2~3일이다. 평택 본사 전환으로 M1은 평택→하이퐁 5일이 되었다. ‘평택 노선 재설계 승인’ 절.)*
3. **나라별 동료:** 새 거점 국가(네덜란드·영국·그리스·모로코·남아공·케냐·미국·파나마·브라질·호주·아랍에미리트·인도·홍콩)의 동료는 아직 만들지 않았다. 동료 60종의 만남 지역은 1장 6개국과 공통 그대로다.

**비판적 검토:**
- 중국 항만은 세계 100대 항만 물동량의 40%를 넘는다. 그런데 거점은 상하이와 홍콩 둘뿐이라 중국 비중을 과소 대표한다. 2장에서 닝보·선전·칭다오를 같은 권역의 보조 항만으로 둘지 정해야 한다.

## 참고 연구 적용: 일괄 확정·막힌 이유·운영표·직무 배지 — 2026-10-05

대상: [references/playthrough_research_2026-10-05](../references/playthrough_research_2026-10-05/HANDOFF.md)의 구현 제안 REF-01~14. 항목별 채택 여부와 남은 일은 [RESEARCH_APPLICATION.md](RESEARCH_APPLICATION.md)에 있다.

**자료를 어떻게 썼는가:** 연구는 숙련 제작자의 공략·실황 영상 자막 요약이다. 이 게임의 대상인 처음 접하는 학습자가 어디서 막히는지를 대표하지 않는다. 그래서 효과의 근거가 아니라 ‘혼란이 생길 만한 지점’의 가설로만 썼다. 영상 속 수치는 계수로 쓰지 않았다. 효과는 설계서 11절의 사용성 목표로 따로 확인한다.

**이번에 반영한 것 (M2a 범위 안):**
- **REF-02 일괄 확정:** 견적 수락 명령에 선택 항목 `plan`(준비 담당 직원·운송편)을 붙일 수 있다.
  - 엔진은 상태 사본에서 수락→배정→예약을 차례로 시험한다. 모두 성공할 때만 반영한다.
  - 하나라도 실패하면 수락까지 철회하고, 실패한 단계와 이유를 돌려준다(‘일괄 확정을 철회했습니다 — 운송편 예약 불가: …’).
  - 새 규칙을 만들지 않고 기존 `assignTask`·`bookSailing` 검사를 그대로 쓴다. 그래서 단계별로 명령한 결과와 장부가 같다(테스트로 대조).
  - 기존 단계별 명령(견적만 수락→배정→예약)도 그대로 남겼다. 학습자가 단계의 의미를 하나씩 익히는 경로가 필요하기 때문이다.
- **REF-10 막힌 이유:** 계약마다 ‘다음 할 일’과 막힌 이유를 엔진 함수(`src/engine/progress.ts`)로 계산한다. 화면은 읽기만 한다.
  - 9종: 준비 미배정, 이 속도면 출항 불참, 운송편 미예약, 다음 편도 납기 초과, 예약한 편 납기 초과, 남은 편 없음, 하역 중단 대기, 관세 미지급, 수금 대기.
  - 3단계: 참고(기다리면 됨), 조치 필요, 위험(그대로 두면 비용·지연).
  - 준비 완료 예상일은 ‘하루 마감 때 업무 진행 → 같은 날 출항 처리’ 순서를 따른다. 출항일에 끝나도 실을 수 있다.
  - 표시한 ‘출항 불참’이 실제로 일어나는지 엔진 진행 결과와 대조하는 테스트를 두었다. 표시와 결과가 어긋나면 학습자가 화면을 믿지 않게 되기 때문이다.
- **REF-05·01 운영표:** 카드 옆에 같은 상태·같은 필터(전체/대기/업무 중)를 쓰는 표를 두었다. 행을 고르면 같은 카드가 선택된다. ‘업무 중’ 판단은 카드·표·계획 선택·자원 패널이 모두 같은 함수(`runningTaskOf`)를 쓴다.
- **REF-12 의미 분리:** 직무는 도구 모양 배지와 글자로, 근무 상태는 기호(●/○)와 글자로 나타낸다. 속성(문양 칩)과 섞지 않는다.

**바꾸지 않은 것:** 엔진 규칙 판본, 시나리오 수치, M1·M2 검산 값, 저장 판본. `plan`은 명령의 선택 항목이라 이전 저장의 명령 기록도 그대로 읽힌다.

**비판적 검토:**
- 일괄 확정은 클릭 수를 줄인다. 대신 ‘수락하면 자금이 묶이고, 배정하면 직원 시간이 묶이고, 예약하면 선복이 묶인다’는 단계별 인과가 한 번에 지나가 버릴 수 있다. 학습 목표가 이 인과를 이해하는 것이라면 첫 계약은 단계별 경로로 안내하는 편이 낫다. 사용성 시험에서 두 경로의 이해도를 비교해야 한다.
- 막힌 이유는 지금 엔진이 아는 원인만 보여 준다. 창고·통관 대기열·환율처럼 아직 모형에 없는 병목은 ‘막힌 곳 없음’으로 보일 수 있다. 모형이 커질 때마다 원인 목록과 대조 테스트를 함께 늘린다.
- 연구 표본은 게임별 5편이고, 같은 제작자의 연속 에피소드가 섞여 있다(대항해시대·Software Inc.·Two Point Hospital 각 2편, 길드 3의 Nivarias 두 채널). 이것으로는 어떤 혼란이 흔한지 빈도를 말할 수 없다.

## M2a-2 동료 영입 구현의 세부 결정 — 2026-10-05

Codex 구현에서 지시서에 없던 판단을 Claude가 검수하며 받아들인 것들이다.
- **업무 ID:** 조사 업무는 `SCOUT-<장소>`, 의뢰 업무는 `RECRUIT-<후보>`다. 기존 계약 업무 순번(`TASK001`…)을 바꾸지 않기 위해서다.
- **고용과 근무 시작:**
  - 고용 확정(`employed`)과 근무 시작일(`availableFromDay = 고용일 + 1`)을 나눈다.
  - 화면 목록·배정·급여는 근무 시작일부터 직원을 포함한다.
  - 고용 당일 카드에는 ‘고용됨 — 다음 날부터 근무’가 보인다.
- **계약금 자금 기준:** 계약금은 그 통화의 현금 − 미지급 의무로 판단한다.
  - 당일 급여는 따로 예약하지 않는다. 이 때문에 급여가 미지급으로 밀릴 수 있다는 지적이 있었으나, 검증자 3명이 모두 기각했다.
  - 계약금이 0원이면 장부 기록 없이 고용한다.
- **거절된 명령:** 거절된 명령은 상태를 바꾸지 않는다. 업무는 배정 검사를 통과한 뒤에만 넣고, 업무 ID 유일성을 불변 조건으로 지킨다.

- **화면:**
  - 면담 수치는 저장하지 않는 미리 보기로만 계산하고, 고용 가능 여부는 엔진이 판정한다.
  - 미발견 후보는 패널·카드·운영표·속성 어디에도 드러나지 않는다.

**비판적 검토**
- **Codex 첫 구현:** 완료 조건은 충족했다. 그러나 테스트 하나가 다른 규칙(직원이 바쁨)에 먼저 걸려 정작 그 규칙을 증명하지 못했다. 반박 검증(검증자가 일부러 오류를 넣어 보는 방식)이 없었다면 놓쳤을 결함이다.

**Claude가 정한 것**

## TASK-0012 문화 활동 화면 — C+A 혼합안 (2026-10-06)

**과정:** 사용자 지시 ‘1’에 따라 핵심 60초·학습 증거·선택 기준(C1~C8)을 먼저 고정하고(`docs/ai/design/TASK-0012-scene-brief.md`), 움직이는 시안 3개를 만들어 기준으로 채점했다. 기록과 시안 파일은 `docs/ai/design/TASK-0012-scene-compare.md`, `docs/ai/design/TASK-0012-mockups/`에 있다.

**점수:** C 기록장 중심형 83, A 패널형 78, B 도시 장면형 75(가중치 합 100, 탈락 없음). 학습은 C(44/50), 구현은 A(19/20)가 앞섰다. 관점마다 AI 심사자 1명이 매긴 점수이고 학생 반응이 아니므로, 5점 차이는 오차 범위 안으로 본다.

**사용자 결정:**
1. **C+A 혼합안.** C의 학습 장치(4칸 기록 틀과 안내 질문, 주제 제목, 출처 줄, 움직이지 않는 ‘넓혀 읽지 않기’ 표시)를 A의 구조(칸 안에 그리는 패널, 500ms 두 번 누름 막기, 기다리는 업무 경고, 결과의 ‘쓴 것’)에 담는다. B에서 ‘직원을 고르는 순간 미리 보기가 드러남’과 머리 문장을 가져온다. 수집 유도 문구(‘빈 쪽’·‘채우려면’)와 애니메이션은 빼고, 경험치는 보상 배지처럼 보이지 않게, ‘바뀌지 않는 것’은 경험치보다 눈에 띄게 한다.
2. **하루 진행 뒤 결과: 읽던 자리 유지 + 알림.** 화면과 초점은 TASK-0014 규칙대로 두고, 알림의 ‘결과 보기’ 한 번으로 결과 카드에 간다. 다음에 ‘부산 현지’를 열면 새 기록이 맨 위에 있다.

**검토한 다른 안과 남는 위험:**
- 학습 심사자는 결과를 저절로 펼쳐 학습 증거 1·2를 건너뛸 수 없게 하자고 권했다. 사용자는 T2의 반복 ‘하루 진행’을 끊지 않는 쪽을 골랐다. 남는 위험은 학생이 결과를 열지 않고 지나가는 것이다. 사용성 시험·2차 확인에서 ‘결과 보기를 누른 비율’과 학습 증거 1·2 응답을 함께 관찰한다.
- 혼합안은 직접 잰 시안이 아니다. 지시서에 C1~C8과 1024·1180·1366px 배치 측정을 완료 조건으로 넣고, 검수 때 다시 채점한다.

**지시서 작성 때 Claude가 정한 기본값 (2026-10-06, 사전 조사 4갈래: 엔진 계약·화면 연결 지점·혼합안 명세·3판 실제 배치 측정):**
- **배치:** 진입점은 거래 칸 머리 오른쪽 위의 ‘부산 현지’ 탭(흐름 밖, 아무것도 밀지 않음)이다. 열면 패널이 주 열 맨 위(거래 위)에 생긴다. 6개 후보를 7개 기기 프로필로 쟀다.
  - 시안 A 자리(거래 아래 줄)는 진입점이 3,020~3,155px 아래였다.
  - 시안 C 자리(오른쪽 칸 위)는 닫혀 있어도 동료 칸을 101~108px 밀었다. 열면 300px 폭에서 결과 네 줄이 475px가 되어, 알림이 있을 때 4개 기기에서 한 화면에 들어가지 않았다.
  - 탭 자리는 닫힌 상태의 모든 제목 위치가 3판과 0px 같았다. 결과 네 줄은 12/12 한 화면이었고, 격자 영역도 바꾸지 않는다.
  - 흐름 심사자는 시안 B의 ‘거래 칸 머리 진입점’을 옮기지 말라고 했다. 그 지적은 B의 자동 열림 시트와 묶인 것이었고, 이번 탭은 측정에서 무엇도 밀지 않았다. 남는 위험은 탭이 거래의 일부로 읽히는 것이다. 사용성 시험에서 학생이 찾는지 관찰하고, 못 찾으면 오른쪽 칸 위 카드(동료 +101~108px 감수)로 바꾼다.
- **출처 이름:** 결과 카드의 출처는 전체 이름(‘출처 시장 상인 윤서(1명)’)으로 쓴다. 짧은 이름(‘윤서’)은 엔진이 로그를 만들 때만 계산한다. 화면이 같은 규칙을 다시 쓰면 엔진 문구를 다시 만드는 셈이 된다. 전체 이름의 역할(‘시장 상인’)이 ‘한 사람의 말’이라는 점도 드러낸다.
- **‘바뀌지 않는 것’ 값:** 결과 카드에도 필요하다. 그래서 엔진의 고정 문자열을 같은 값의 상수로 내보내는 것만 화면 작업에 허용한다(엔진 동작 불변).
- **문구:** 시안 비교 때 제시한 미리 보기 첫 줄 ‘이 쪽에 드는 것’은 ‘이 활동에 쓰는 것’으로 바꾼다. ‘쪽’은 시안 C의 기록장 쪽(page) 구조에서 온 말인데, 혼합안에는 그 구조가 없다. ‘쓰는 것’은 결과 카드의 ‘쓴 것’과 짝이 되어 기회비용(학습 증거 3)을 앞뒤로 잇는다.
- **그 밖:**
  - 패널은 플레이어가 닫을 때까지 열린 채 둔다(읽던 자리 유지). 열린 채 며칠 진행하면 거래가 밀리는 것은 관찰 항목으로 둔다.
  - 자리 안 ‘빼기’는 두지 않는다(같은 자리를 다시 누를 때의 사고).
  - 직원 고르기와 패널 열고 닫기에도 500ms 두 번 누름 막기를 건다.
  - 원화 보고서에 ‘현지 활동비’ 행을 더한다. 지금은 행의 합이 운영 손익과 20,000원 어긋난다(기존 결함).
  - 성장 알림 ‘+10 경험치’가 결과보다 먼저 눈에 띄는 문제(Q6 오개념 위험)는 이번 범위 밖이다. 관찰 항목으로 둔다.

**지시서 비판 검토 뒤 고친 것 (2026-10-09, 5관점 비판 + 관점별 반박 검증, 지적 80건 중 blocker 2·major 다수 확인):**
- **아직 안 본 결과 (blocker):** 처음 초안은 결과 카드·탭의 ‘새 기록 있음’을 ‘방금 마감한 날’ 하루만 보였다. 그러면 ‘결과 보기’를 누르지 않고 하루를 한 번 더 진행할 때 결과가 맨 위에서 사라진다. 사용자 결정 ‘다음에 부산 현지를 열면 새 기록이 맨 위’가 바로 이 경우를 위한 안전망이므로 고쳤다.
  - 화면 상태 하나(패널을 마지막으로 연 날)로 ‘아직 안 본 결과’를 판정한다. 새 엔진 상태는 없다.
  - 불러오기 뒤에는 ‘방금 마감한 날’ 규칙으로 돌아간다(받아들이는 대가).
- **읽던 자리 기준 (blocker):** 기준 후보였던 미리 보기 제목은 하루 진행 때 사라진다(고른 직원을 지우므로). 그래서 가장 흔한 흐름(넣고 패널을 연 채 하루 진행)에서 결과 카드 높이만큼 화면이 밀렸다. 하루 진행 뒤에도 남는 제목(‘② 갈 직원 고르기’ 줄 등)만 후보로 쓰고, 남은 첫 후보로 보정한다.
- **격자 줄 높이:** 패널을 열어 주 열이 길어지면 오른쪽 칸의 ‘자원 예약’·‘오늘 할 일’이 최대 320·639px 밀렸다(측정). `grid-template-rows: auto auto 1fr` 한 줄로 밀림 0을 확인했다. 격자 영역 문자열은 그대로이고, 1일·2일 닫힌 상태와 전 세계 지도 배치도 3판과 같다.
- **문구 (학습 관점):**
  - 출처 줄 ‘아직 확인하지 않은 기록’ → ‘다른 출처로 아직 확인하지 않은 기록’(‘안 읽은 기록’으로 읽히는 것을 막는다).
  - 활동 카드의 ‘다녀온 직원’ 줄을 뺐다. 직원 6명 × 활동 3의 채울 표가 되고 첫 완료 경험치와 합쳐 수집 순환을 만든다. 같은 정보는 기록장과 엔진 거절 문장에 있다.
  - 금융센터 ‘주식(P1)·상장(P2) 없음’ → ‘주식 거래와 상장(회사 주식을 시장에 내놓기)은 이번 판에 없습니다’. P1·P2는 개발 단계 부호라 학생에게 뜻이 없다. P0-CITY-01 단언(미구현을 완료된 서비스처럼 보이지 않음)은 그대로 지킨다.
  - 그 밖: ‘N일’이 기간과 날짜로 섞이던 곳(‘기간 1일’, ‘하루 업무(2일)’), 알림에 주제 제목(‘한 상인의 …’), RF-1 문장을 확정형으로, ‘회사 보고서’로 이름 통일, 함께한 활동은 사건마다 한 줄, ‘직접 경험 기록’이 능력·처리량을 바꾸지 않는다는 안내.
- **시험 설계:** RF-1 시험은 기본 M2 자금으로 90일에 만들면 자금 부족으로 거절되어 올바른 구현에서도 실패했다(실험 확인). 캠페인 2일 합성 설정으로 바꿨다. 하네스의 실제 동작(모르는 선택자, 스크롤 함수)도 사실대로 고쳐 적었다.
- **측정 기준:** ‘미리 보기 한 화면’의 실제 여유는 72px 알림 자리를 빼면 1366×657 터치에서 12px다(사전 조사의 ‘84px’는 72px를 빼지 않은 값으로 틀렸다). ‘하루 진행 뒤 스크롤 0px’는 패널을 닫은 경우에만 적용하고, 연 경우는 ‘보던 제목의 화면 위치 변화 ±1px’로 고쳤다.

## 자료 청크 분리와 빌드 크기 한도 (2026-10-10, TASK-0026)

- **반영:** `vite.config.ts`의 `codeSplitting.groups`로 `data/*.json`을 코드와 다른 청크(data)로 나눈다. 두 청크 모두 첫 화면에서 받는다(코드는 script, 자료는 modulepreload). 목적은 청크마다 크기 한도를 관리하는 것이다. 속도나 캐시 이득은 약속하지 않는다(코드만 바뀌어도 자료 청크 이름이 바뀔 수 있다). `PACKAGE_STATUS.json`·`src/assets/manifest.json`은 data 폴더 밖이라 코드 청크에 남는다.
- **한도:** JS 청크 하나 500,000 B, 첫 화면 JS·CSS 합계 600,000 B·gzip 140,000 B, 글꼴(스타일시트 + 파일) 5,000,000 B. 넘으면 실패다. 검사기는 `tools/check_bundle_size.mjs`(종료 0 통과, 1 한도 초과, 2 사용법 오류·읽을 파일 없음·읽기 오류). 자동 검사 묶음은 빌드가 성공했을 때만 재고, 실패하면 남은 옛 dist를 재지 않고 실패로 센다.
- **지금 값:** 코드 212,001 B, 자료 317,893 B, 첫 화면 555,863 B·gzip 127,974 B, 글꼴 4,169,241 B. 첫 화면 원본 합계의 여유가 약 44 KB라, 큰 화면 기능을 더할 때 이 검사가 먼저 걸린다. 그때 캐릭터 자료를 화면·엔진이 읽는 칸만 남겨 빌드하는 안 B(단일 청크 기준 529,657 → 329,040 B, Claude 조사)를 검토한다. 안 B는 읽는 칸 목록·설계 전용 칸의 위치·자료 검사기와의 관계를 먼저 정해야 한다.

## M2a-5 읽기 함수·주간 병목 표 (2026-10-10, TASK-0028)
