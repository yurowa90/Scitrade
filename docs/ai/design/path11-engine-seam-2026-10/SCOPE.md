## 1. (ㄱ) H33-3 장면의 읽기 함수

공통 원칙
- 읽기 함수는 상태를 바꾸지 않는다. 시뮬레이션 결정에도 쓰이지 않는다.
- 그래서 **결정성과 기본 `run` 400회 cmp에 영향이 없다.** sim은 읽기 함수를 부르지 않는다. 다만 새 함수를 `readers.ts`(첫 화면 `index` 청크)에 두면 첫 화면 크기는 는다(2절).
- 미래 누설 금지: 대손·지연 확률, 앞으로 나올 견적의 내용은 보이지 않는다. 공개 **일정**은 자료에 정해진 사실이라 보여도 된다(세션 B README 2절).

### 1.5 ‘대손 기대’ — 화면 값으로 두지 않는다

- 대손 확률(`pDefaultBpByGrade`·`defaultFor`)을 화면에 보이면 미래 누설이다. TASK-0067a 1절 6과 세션 B README 2절 ‘보이지 않는 것’이 이를 금지한다.
- 대신 보이는 것
  - 선택하는 순간: 거래처 등급(A·B·C)과 ‘늦게 낼 수 있음’ 문구(1.1의 `grade`)
  - 일어난 뒤: 확정 대손 기록(원장 `BAD_DEBT` 분개, `WRITTEN_OFF` 청구서)과 연체 상태(1.3의 `overdueDays`)

### 1.7 중간 재무상태(판단거리 3)

- **새로 기록할 것은 없다.** 원장 분개에 `day`가 있다(`ledger.ts:71`). 그래서 지난 날짜 d의 계정 잔액은 `day ≤ d`인 분개를 더해 다시 계산할 수 있다. 재고·청구서 상태도 분개와 계약에서 같은 방식으로 복원한다.
- 함수(**새**, 안): `balanceSheetAt(s, config, asOfDay) → { assets: [...], liabilities: [...], equity: [...] }`
  - 같은 함수로 ‘오늘 재무상태’(`asOfDay = s.day`)와 30·60일 마감을 함께 낸다.
- **판단거리 3과의 관계**
  - 3(가) 중간 재무상태를 둔다: 이 함수가 필요하다. 30·60일 고정 마감인지 ‘오늘’인지는 화면 쪽 선택이다.
  - 3(나) 끝에만 둔다: 이 함수는 필요 없다. 다만 세션 B 실측대로 90일 끝에는 매출채권이 ₩0이라 H33-3 기제가 결산에서 보이지 않는다[세션 B 실측].
- 결정성·400회 영향 없음.

### 1.8 원화 환산 결산(판단거리 2)

  - 재무상태: 마감일 환율로 환산한다.

### 2.5 위험

1. **지연 청크 실패(오프라인·느린 학교망)**
   - 지금 `ui/lazy.ts`는 묶음마다 첫 시도와 **재시도 한 번**만 허용한다. 그 뒤에는 `ScreenLoadExhaustedError`로 ‘저장하고 새로 고침’을 안내한다(`main.ts:60-68`). 서비스 워커는 없다(grep 0건).
   - 운영 엔진을 지연 청크로 옮기면, 운영 시나리오에서는 **게임 진행 자체**가 그 청크에 기대게 된다. 지금 지연 청크는 화면 일부만 다룬다.
   - 불러오기 실패의 영향이 ‘칸 하나가 안 보임’에서 ‘시나리오에 못 들어감’으로 커진다.
   - 완화
     - 운영 시나리오 진입과 운영 저장 불러오기는 이미 `ensureOpsScreens()`를 기다린다(`main.ts:1550`, `:1607`). 운영 엔진 청크를 같은 약속에 묶으면, 실패할 때 지금과 같은 안내로 끝난다. 진행 중에 실패하는 일은 없다.
     - 진행 중에 청크가 처음 필요해지는 경로가 남지 않는지 시험으로 고정한다(정적 분석 또는 청크 그래프 검사).
2. **iPad Safari**
   - 동적 import 자체는 지원된다. 다만 메모리 압박으로 탭이 다시 읽히면 그때 청크를 다시 받는다. 그때 망이 없으면 위 1의 안내로 끝난다.
   - **실기기에서 확인하지 않았다.** 지시서 완료 조건에 Playwright WebKit 진입 시험과 오프라인 재시도 시험(지금 `code-split.test.ts` 방식)을 넣기를 권한다.
3. **결정성과 골든**
   - 등록식 주입은 함수 호출 경로만 바꾸므로 결과는 같아야 한다.
   - rules-1~3 골든, 400회 cmp, 판본 2 SHA256SUMS 다섯 파일 재현(TASK-0071 방식)을 완료 조건으로 둔다.
   - 등록 전에 운영 함수를 부르면 예외를 내게 해서, 조용히 다른 값이 나오지 않게 한다.
4. **sim·시험 경로**: `run.mjs`·vitest는 번들을 쓰지 않는다. 다만 등록식이면 sim 진입점에서도 등록을 해야 한다. 등록을 빠뜨리면 3의 예외로 바로 드러난다.

## 3. (ㄷ) 지시서를 하나로 할지 둘로 나눌지

**권고: 둘로 나눈다. 순서는 ‘엔진 분리 → rules-4 플레이 도입’이다(허브 기본안과 같다).**

| 지시서 | 범위 | 검증 성격 |
|---|---|---|
| ① 엔진 분리 | 2.3의 등록식 주입, 후보 A(+B·C는 선택), 화면 쪽 정적 import 옮기기, 지연 실패 시험 | **동작 불변 정리.** 완료 조건은 바이트 동일(골든·400회·SHA256SUMS)과 첫 화면 gzip 감소다 |
| ② rules-4 플레이 도입과 읽기 함수 | 1.9의 갈래 하나, 1.1~1.8의 읽기 함수, 형식 왕복 시험 | **새 동작.** 완료 조건은 새 시험과 첫 화면 gzip이 ① 뒤 기준보다 늘지 않음(새 코드는 운영 청크로) |

- 나누는 이유
  1. 검증 성격이 다르다. ①은 ‘아무것도 바뀌지 않음’을, ②는 ‘새것이 맞음’을 보인다. 한 지시서에 섞으면 바이트 비교가 어느 변경 때문에 깨졌는지 가를 수 없다.
  2. ①은 판단거리 답과 무관하다. 그래서 지금 바로 할 수 있다. ②는 판단거리 1·2·3의 답을 기다린다.
  3. ②의 새 코드가 처음부터 운영 청크에 들어가므로 첫 화면 예산을 다시 쓰지 않는다.
- 1(나)(형식 7과 함께)로 답이 오면 ②를 둘로 더 나눈다.
  - ②-a: rules-4 시나리오와 형식 7 이관, 1.6 (나) 칸
  - ②-b: 읽기 함수
  - 저장 이관은 되돌리기 어려운 변경이라 따로 검수하는 편이 안전하다.
- **반대 의견도 적어 둔다.** ①의 비용(등록식 주입, 화면 import 정리)이 크고 실제 절감이 상한보다 많이 작으면, 대안이 있다. 후보 0·B·C만 먼저 하고 ①은 경로 6·7 앞으로 미룬다. 판단 기준은 ① 지시서의 첫 조사(2.3 화면 쪽 사용처)에서 나온다. 그 조사 결과 실제 절감이 약 5 KB에 못 미칠 것으로 보이면 그 시점에 멈춤 보고를 하게 한다[문턱 5 KB는 2.4의 경로 11 추가 추정치 상한에서 잡은 값이다].
