# D14 지도 상세 — 설계 검토 (세션 B, 2026-10-11)

TASK-0035 지시서를 쓰기 전의 설계 검토다. D14는 결정 묶음 395~411행에 있고, 사용자가 2026-10-10에 추천안 ‘가’로 정했다. 가안은 ‘거점·관문·배를 버튼으로 만들고(키보드·터치), 누르면 지도 아래에 읽기 전용 상세 칸’이다.

선행 TASK-0025(이번 항로 지도 폭 맞춤)는 병합됐다(`c896c8a`). 여기 적은 측정은 개발 브랜치 `5d59ff3` 빌드(평택판 배포본과 같음)에서 했다.

## 1. 측정: 지도 표시는 버튼이 되기에 너무 작고 너무 가깝다

`hubgap.js`(저장소 밖 측정기 `kb/blib.js`를 쓰는 스크립트)로 쟀다. 7개 프로필에서 지도의 거점 휘장·해협 표시마다 중심과 크기를 재고, 모든 쌍의 거리를 셌다. 원자료는 `hubgap-5d59ff3.txt`다.

| 프로필 | 이번 항로: 표시 수 / 지름 / 44px보다 가까운 쌍 / 가장 가까운 쌍 | 전 세계: 표시 수 / 지름 / 44px보다 가까운 쌍 / 가장 가까운 쌍 |

이 측정에서 나오는 것:
- **터치 크기 규칙을 지킬 수 없다.** 휘장은 지름 7.2~21px다. 이 저장소의 터치 대상 규칙은 44px다(DECISIONS 882·884행, 1064행 `any-pointer: coarse`). 휘장을 키우면 지도가 가려지고, 누를 자리만 44px로 넓히면 서로 겹친다.
- **겹침은 ‘이번 항로’에서도 생긴다.** 시험 기기인 iPad 3종과 1366 두 종에서 평택–부산이 33px, 말라카–싱가포르가 30.5px다.
- **전 세계 보기는 버튼 27개가 Tab 순서에 들어간다.** 결정 묶음이 위험으로 짚은 그대로다(‘버튼이 많아지면 Tab 순서가 길어진다’). TASK-0024에서 하루 진행 → 오늘 할 일 Tab 수를 26 → 10으로 줄였는데, 지도 버튼이 들어가면 한 열 화면에서 다시 늘어난다.
- **파나마는 도시와 운하가 사실상 같은 점이다(1.5~3px).** 어떤 크기로 그려도 누른 사람이 무엇을 골랐는지 알 수 없다.

## 2. 또 하나: 노선 근거에 실명 선사가 있다

가안의 상세에는 ‘노선 근거(선사 요일표·확인 수준)’가 들어 있다. 그런데 `data/routes.json`의 `schedule_basis.carrier_service_ko`는 실제 선사와 서비스 이름이다. 세션 공통 규칙은 ‘실제 회사·선박 이름은 게임 밖 근거 자료에만 쓴다’이다(SESSION_TREE ‘조사’).

그래서 화면에는 이름을 빼고 이렇게만 보인다: ‘선사 요일표로 확인함(2026-10-09), 오차 ±1일. 게임은 2일 첫 출항·7일 간격으로 단순화함’. 이 칸들은 `status`·`checked_on`·`tolerance_days`·`note_ko`에서 가져온다. 이건 규칙을 지키는 일이라 사용자 결정은 필요 없다.

## 3. 제안: 가안의 목적은 그대로, 고르는 방법만 바꾼다

가안의 목적은 두 가지다. 첫째, iPad에서 마우스 올리기 없이 선정 근거에 닿는다. 둘째, 키보드로도 닿는다. 이 목적은 그대로 두고, ‘표시 하나하나를 버튼으로’라는 수단만 바꾼다.

**안 가′ (권장): 목록 하나 + 지도 누르기는 가까운 후보 고르기**
1. **지도 위 ‘거점·해협 고르기’ 목록 하나.**
   - 형태는 브라우저 기본 `<select>`, 또는 같은 역할의 단추 하나 + 목록이다.
   - 묶음은 ‘이번 시나리오 거점 / 1장 예정 / 세계 미리 보기 / 해협·운하 / 운항 중인 배’다.
   - Tab 정지점은 하나다. iPad에서는 기본 고르기 바퀴가 떠서 44px 문제가 없다.
   - 보이는 지도(이번 항로/전 세계)에 있는 것만 넣는다.
2. **지도를 누르면 누른 점에서 가까운 표시를 찾는다.**
   - 찾는 거리는 22 CSS px다(44px 지름의 절반).
   - 하나면 그것을 고른다.
   - 둘 이상이면 상세 칸에 ‘이 근처: 파나마(도시) · 파나마 운하’를 단추로 보여 고르게 한다. 이 단추들은 상세 칸 안의 보통 HTML 단추라 44px를 지킬 수 있다.
   - 하나도 없으면 아무것도 하지 않는다.
3. **고른 것은 지도에서 강조하고, 지도 바로 아래 상세 칸에 보인다.**
   - 강조는 휘장 둘레에 테두리 고리를 두르는 것이다. 색만 바꾸지 않고 모양으로도 보인다.
   - 상세 칸은 `aria-live="polite"`다. 목록·지도·상세 칸이 같은 고른 값을 쓴다.
   - 전 세계 보기에서 고른 것이 틀 밖이면 가로 스크롤을 최소만 옮긴다.
4. **상세 칸 내용(읽기 전용).**
   - 거점: 이름·역할, 선정 근거(`basisKo`), 메모(`noteKo`), 개방 단계, 이 거점을 지나는 이번 시나리오 노선과 그 근거(실명 빼고, 위 2절), 이 거점이 출발·도착인 예약 화물 수.
   - 해협·운하: 연결하는 바다(`connectsKo`), 사건 연결(`eventHookKo`), ‘세계 확장(2장)에서 연결 예정’.
   - 배: 출항편, 실은 화물, 하역 대기 여부.
   - 지금 SVG `<title>`에 있는 글을 그대로 옮긴 것이다. 새로 쓰는 학생용 문장은 목록 이름표와 안내 한 줄뿐이다.
5. **닫기.** 상세 칸의 ‘닫기’ 단추와 Esc(D13 ‘맨 위 칸’ 목록에 한 칸 더함)로 닫는다. 닫으면 연 곳(목록 또는 지도 틀)으로 초점을 돌려준다.
6. **안내 문구.** `main.ts` 394행의 ‘거점에 마우스를 올리면 선정 근거가 보입니다’를 바꾼다. 새 문구는 ‘목록에서 고르거나 지도의 거점·해협·배를 누르면 지도 아래에 자세한 내용이 나옵니다’다.
   - SVG `<title>`은 마우스 사용자를 위해 남긴다.
   - SVG의 `role="img"`와 `aria-label` 요약은 그대로 둔다. 상세는 목록과 상세 칸이 맡는다.

**안 가 (결정 그대로): 표시마다 버튼, 방향키로 이동하는 그룹**
- Tab 정지점은 그룹 하나로 두고 방향키로 옮긴다(APG 툴바 방식). 그러면 Tab 길이 문제는 피한다.
- 남는 문제가 둘 있다.
  - 1절의 터치 크기·겹침 문제가 그대로다. 파나마처럼 겹친 표시는 손가락으로 고를 수 없다.
  - 전 세계 지도 틀은 이미 방향키를 가로 스크롤에 쓴다(`mapPresentation`의 안내 ‘화살표 키를 눌러 보세요’). 방향키의 뜻이 지도 틀과 그룹 안에서 갈린다.

**안 다: 툴팁 문구만 고침** — 결정 묶음 그대로 iPad 문제를 풀지 못한다. 고르지 않는다.

**권장 근거.**
- 1절 측정상 가안은 터치 규칙(44px)과 겹침을 함께 만족할 수 없다.
- 가′는 기본 `<select>`로 키보드·터치·화면 읽기 프로그램을 모두 덮고, Tab 정지점은 하나만 는다.
- 지도 누르기는 ‘가까운 후보 고르기’로 바꿔 겹친 표시도 가를 수 있다.
- 가안의 ‘나중에 상세에서 행동(노선 비교·계약 카드로 이동)’으로 넓히는 길(안 나)도 그대로 열려 있다.

## 4. 대가와 반례

- **지도를 눌러도 바로 그것이 골라지지 않을 때가 있다.** 22px 안에 둘 이상이면 한 번 더 누른다(전 세계 iPad mini에서 15쌍). 실제로 눌러 보며 고르는 사용자에게는 한 단계가 더 생긴다.
- **목록이 길다.** 전 세계 보기는 27곳 + 배다. 묶음 이름으로 나눠도 길다. 기본 `<select>`는 iPad·크롬북에서 시스템 고르기 화면을 쓰므로 길이 자체는 문제가 적다.
- **한 열(1000px 이하)에서는 지도가 화면 아래쪽이다.** 상세 칸을 열면 TASK-0024의 펼침 띠 규칙(`revealBelow`)으로 칸 머리가 막대 아래에 오도록 최소 거리만 굴린다.
- **크기.** 글과 고르기 코드는 대략 gzip 2~4 KB로 본다(추정, 시제품으로 잴 것). 지금 여유는 약 21.4 KB다(TASK-0028 병합 기록).
