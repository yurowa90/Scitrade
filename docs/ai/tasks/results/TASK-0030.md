## 설계 판단 (지시서에 없던 결정과 이유)

1. 차단 중 준비 업무는 예측 사본에서 당일 배분·진행 고리 동안만 제외한 뒤 원상태로 돌린다. 진행을 건너뛰기만 하면 그 업무가 창고 용량을 소비해 다른 직원의 예측까지 늦어지므로 배분에서도 제외한다. `waitDays`는 기존처럼 창고 배분 부족 일수다. 차단 자체는 창고 대기 일수에 넣지 않는다.
2. 배정 기준은 모든 차단 구간에 대해 `ceil(남은 pt / 직원 처리량) ≤ fromDay − 배정일`이다. 차단이 끝난 구간은 무시한다. 창고 용량은 이 기준에 넣지 않고 날짜별 배분에서 적용한다. 이미 맡은 업무는 `employeeId`를 유지하며, 예측이 끝내 맡기지 못한 업무만 null이다.
3. 수락·예약 성공 직후의 계획 상태와 당시 영입 차단으로 준비 예측을 기록한다. 후속 재예측으로 기록을 덮어쓰지 않는다. 계측기는 출항 당일 활성 예약이 취소되고 해당 계약의 준비 업무가 QUEUED/RUNNING이면 불일치로 센다. 출항 전에 이미 취소한 예약은 제외하고, 여러 예약을 놓쳐도 계약 ID 집합으로 한 번만 센다. 규칙 1의 출력 모양은 그대로다.
4. 재현 시험은 시드 1001의 실제 정책·명령으로 23일까지 진행한 다음, 자료 속성으로 찾은 과거 문제 견적을 명령으로 수락한다. 자료 ID를 하드코딩하거나 인수 명세 17에 행동을 더하지 않았다. 새 예측은 시작 직원 첫 번째에게 28일 배정·33일 완료를 산출한다(27일까지 기존 10pt 처리, 28~33일 12pt). 같은 인력·차단 일정으로 실제 명령을 진행해 모든 대상 업무의 직원·완료일을 대조한다. 정상 정책은 이 계약의 30일 예약 수락을 거절한다.
5. 지시서의 BASE 대체 규칙을 따라 `38ea0b2`를 썼다. 실제 착수 HEAD는 `5d59ff3`이며 작업 트리는 깨끗했다. BASE→HEAD의 기존 차이는 상태·결정·계획·검증·지시서 목록·MANIFEST 문서뿐이다. 검수 출력의 이 문서 차이를 이번 수정으로 세지 않았다.

  - 이 고침은 엔진의 실제 수락 규칙에서 끌어낸 것이지 J6 수치에 맞춰 고른 값이 아니다. 그래도 같은 20시드에서 원인을 찾았으므로 고친 뒤의 J6는 낙관 편향이 있다. 재측정 때 cap30·flat200 조건과 LATE_OK 칸 일치율을 따로 보고해 확인한다.
  - 고친 뒤에도 80%에 못 미치면 그때 J6 기준을 사용자 질문으로 따로 올린다(Q13과 묶지 않는다).
- 순서: Q13(직접 무역 경제 조정)은 직접 무역 화물의 창고 점유를 바꾸므로 표 고침과 상호작용한다. 표 고침을 먼저 하고(TASK-0031 후보), Q13 답이 오면 경제를 조정한 뒤 J1~J7을 한 번에 다시 잰다.

### 정정 (세션 A, TASK-0031 지시서 적대 검토 뒤)

- 검수 3절의 ‘묶음에 매이지 않는 직접 무역 준비 pt가 빠진다’는 틀렸다. `acceptedPrep`은 묶음 공급 견적의 직접 무역을 `buyOfferId`로 이미 센다. 실제로 빠지는 것은 묶음 0(`config.offers`, 시작 견적) 계약의 준비 pt다. 결론(보관 칸이 주원인)은 그대로다.
- 보관 칸 체류의 기준 시점도 바로잡는다. 수락 시험은 출항 처리보다 먼저 일어난다. 그래서 화물이 수락을 막는 날 수는 `출항일 − 수락일 + 1`이다. TASK-0031에 반영했다.
