## 설계 판단 (지시서에 없던 결정과 이유)

- `receivedForInvoice`를 `risk.ts`에 두어 수금·채권 읽기·불변식이 동일한 분개 ID 정의를 공유한다. 현금 합만 읽고 상태를 추가하지 않는다.
- `applyReceipt`는 그대로 유지했다. 부분 수금만 금액 인수를 받는 `applyPartialReceipt`로 처리한다. 0원 줄은 기록하지 않고, 같은 수금 ID는 중복 반영하지 않는다.
- 시장 주선 견적은 1일 `operations.offers`에 없었다. 공개 함수로 다음 공개일까지 진행해서 찾고, 수락 가능하고 준비를 마쳐 실제 출항·완료하는 첫 편을 골랐다. 이는 지시서의 ‘시장에서 찾고 출항하는 편’ 조건을 구현한 선택이다.
- 공유 무역 구동기는 수락 전 환전을 `planState`로 시도하고, 거절되면 해당 쌍을 즉시 건너뛴다. 마지막 대조에서 이 처리를 명시했으며, 새 시험 34개와 시간 외 모든 진단 JSON 값(선택 시드·손익·노출 수)이 이전 실행과 같았다.
- 테스트와 변형은 sim/d03/runSuite 없이 엔진 공개 함수만 사용했다. 순수 함수 오라클과 탐색 범위는 2001~2200이다.
- 커밋 금지 때문에 **작업 뒤 결과 커밋의 archive 빌드**는 수행할 수 없다. BASE `git archive` 사본에 허용된 최종 파일만 덮은 `.git` 없는 사본으로 코드 증가를 비교했다. 두 사본 모두 빌드 표시 `dev`이며, 새 커밋 뒤 실측이라고 주장하지 않는다. 허브 커밋 뒤 최종 archive 측정이 남는다.

### 불변식 네 문장

검사는 모두 `operationsProblems`의 운영 설정 조기 반환 뒤에 있다. 날짜는 넣지 않는다.

1. `{청구서}: 받은 금액({받은})이 청구액({청구액})을 넘습니다`
2. `{청구서}: 수금 완료인데 받은 금액({받은})이 청구액({청구액})과 다릅니다`
3. `{분개}: 클레임 분개는 직접 무역 계약에만 있어야 합니다`
4. `{분개}: 클레임({금액})이 늦은 감액 뒤 판매액({판매액})을 넘습니다`

①~③의 저장 사본은 해당 새 검사만, ④는 ①·④만 거부하는 것을 확인했다. 원본 저장 수락, `SaveError`, 정확 문장·ID 포함과 다른 새 문장 부재를 함께 단언한다.

## 범위 밖 발견

- `operations.ts` `paymentDefaultStatus.recovery.nextReceipt`는 지난 청구 결제일과 청구 전액을 그대로 낸다. 부분 수금 뒤 남은 금액·실제 계획일을 뜻하지 않는다. `src/ui/money-alerts.ts`의 ‘다음 수금’도 같은 한계가 있다.
- `progress.ts` `contractProgress`는 D 이후 미수도 ‘오늘 하루 진행 때 전액을 받습니다’라고 설명한다.
- `src/ui/schedule.ts`의 `RCV:` 행은 `invoice.dueDay`와 청구 전액, `src/ui/main.ts`의 `nextReceipt`와 계약 카드 ‘미수’도 청구 전액을 보여 준다.
- `src/ui/main.ts` `accountKo`에 `SALES_ALLOWANCE` 번역이 없어 계정 원문이 보인다. 기존 결산의 매출·원가 표에 에누리 구분 줄은 없고, `OVERDUE`도 기존 미수 표시로 묶인다. 순손익 자체는 이번 `summarize`로 감액을 포함한다. rules-3 화면은 아직 없으므로 지정대로 수정하지 않았다.
- 미수 비용은 환율 노출과 원화 지급 압박뿐이다. 이자·대손·보험 회수는 구현하지 않았다(설계 5.2).
- 기존 그림 도구 시험에서 Pillow `Image.getdata` 폐기 예정 경고가 나왔다. 해당 시험은 통과했고 이번 범위 밖이어서 수정하지 않았다.
- 초기 검증 사본의 `.bin` 링크를 복사할 때 일반 파일로 풀어 BASE 빌드가 `ERR_MODULE_NOT_FOUND`로 실패했다. 원래 링크를 복원하고 다시 빌드·측정해 통과했다. 패키지 설치나 원본 의존성 변경은 없었다.
