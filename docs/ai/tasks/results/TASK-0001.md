## 설계 판단 (지시서에 없던 결정과 이유)

- `isEmployed`는 고용 확정 여부만 판단한다. `isAvailableFromToday`와 `employedDefs`는 근무 시작일까지 확인한다. 따라서 고용 당일 상태는 `employed`지만 기존 카드·운영표·자원 패널·선택 목록·인원 표시에는 다음 날부터 포함한다. 완료 조건 4와 연구 적용 문서의 기준을 따랐다.
- 조사·의뢰 ID는 `SCOUT-<장소>`, `RECRUIT-<후보>`다. 기존 `TASK001` 같은 계약 업무 순번을 유지하고 영입 업무와 충돌하지 않게 했다.
- 발견일과 의뢰 완료일은 실제 마감 처리일을 기록한다. 1일 조사 완료의 `discoveredDay`는 1이며, 다음 입력 시점인 2일에 발견 상태를 보게 된다. 의뢰 완료도 동일하다.
- 후보의 초기 `availableFromDay`는 1로 두지만 `candidate` 상태이므로 배정·급여·목록에는 포함되지 않는다. 고용 시 확정된 다음 날로 덮어쓴다.
- 계약금 지출 판단은 지시대로 해당 통화의 현금에서 미지급 의무를 뺀 값이다. 선택 고용 실패는 장부·후보·업무·의무를 바꾸지 않는다. 기존 명령 처리 규칙에 따라 거절 명령 ID 기록만 남는다.
- 기존 비용 항목의 의미와 영입 없는 경로의 값을 보존했다. 계약금은 급여에 합치지 않고 `recruitmentExpense`로 노출하며, 총손익 `profit`에는 비용으로 차감한다.
- 실제 기존 코드는 계약 업무 ID를 계약 개수로 생성하고, M2 견적은 모두 3일에 만료되며, 기본 직원 일급은 각각 80,000원이다. 고용 뒤 준비 시험은 1일에 계약을 먼저 받아 두었다. 일괄 확정의 고용 당일 거절 시험만 담당 처리량 3pt인 테스트 설정을 사용해 3일에 고용하도록 구성했다. 기존 데이터·기존 테스트 기대값은 바꾸지 않았다.

### 설계 판단 (지시서에 없던 결정과 이유)

- 기존 `assignTask`의 실제 배정 부분을 `assignTaskObject`로 분리했다. 일반 업무는 ID로 찾은 객체를, 영입은 아직 상태에 넣지 않은 새 객체를 전달한다. 거절 가능한 검사를 모두 통과한 뒤에만 객체·로그를 갱신하고 새 업무를 추가하므로 거절된 영입 업무가 남지 않는다.

단계 변형 시험은 `startRecruitQuest`의 `candidate.stage !== 'DISCOVERED'` 검사 한 줄을 실제로 삭제하고 `npx vitest run src/engine/m2a-recruit.test.ts -t '다른 대기 직원'`으로 실행했다. 의뢰 진행 중·면담 가능·고용 완료의 3개 테스트가 모두 실패했다. 실패 출력은 `Expected: "발견한 후보에게만 영입 의뢰를 시작할 수 있습니다."`, `Received: "이미 생성된 업무 ID입니다."`였다. 업무 ID 방어가 있어도 단계 검사가 사라지면 테스트가 통과하지 않음을 확인했다. `finally`에서 원본 검사를 복원한 뒤 전체 95개 테스트가 통과했다.

Python의 `deepcopy`로 만든 자료 사본에 `check_recruitment`를 직접 실행했다. 지난 11종(없는 후보·고용 상태·시작 고용·시작 직원 중복·장소 누락·장소 중복·없는 장소·다른 도시·0 작업량·소수 작업량·음수 계약금 일수)에 영입 필수 키 8종과 장소 필수 키 3종 누락을 추가해 총 22종을 시험했다. 모든 변형이 예외 없이 `ERRORS`를 남겼고, 각 변형에서 33~67개 검사를 계속 수행했다. 원본 자료는 변경하지 않았다.
