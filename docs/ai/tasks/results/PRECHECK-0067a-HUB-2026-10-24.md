## 4. 결론: 허브가 아래 편집을 정확히 적용하면 승인

줄 번호는 검토자 보고를 따랐다. 4.4는 150행이다. feas는 120-121행이라고 적었으니, 편집 전에 위치를 한 번 확인한다.

- **E1 (4.4, 150행, 비교 방법):** "전·후 파일을 `cmp`, 같지 않으면 멈춘다" → "전·후 파일에서 `meta.risk.marketRulesSha256`를 지운 뒤 비교한다(예: `jq 'del(.meta.risk.marketRulesSha256)'` 결과를 `cmp`). 같지 않으면 멈춘다. 이 키의 값은 따로 적는다. 전 값은 BASE 자료의 sha, 후 값은 V2를 더한 `data/market_rules.json`의 sha256과 같아야 한다."
- **E2 (4.4, 150행, 명령):** `--seed-from 2001 --seed-to 2003` → `node src/engine/sim/run.mjs d03 --risk R1 --scenarios SCENARIO_M2_OPS_COS_LAVER --seed-base 2001 --seed-from 1 --seed-to 3 --workers 4 --out /tmp/TASK-0067a-d03-{before,after}.json`. 그 뒤에 한 문장을 더한다. "시드 기준값 없이 기본 시드(1001~)로 돌리지 않는다."
- **E3 (9절 1, 231행):** "d03 cmp가 같다" → "E1 정의로 같고, sha 값은 E1대로다".
- **E4 (8절 변형 12, 225행):** 기대 "d03 cmp 다름" → "risk-runner.test.ts 실패(552행 `profileId`)".
- **E5 (8절 변형 9·10·11, 222-224행):** 기대 "validate_data 실패" → "해당 검사 문장의 FAIL 줄이 나오고, `hash mismatch` 말고 다른 FAIL은 없다".
- **E6 (7절 신규 항목):** 불변식 시험을 더한다. 아래 상태에서 위반 문장이 나오는지 각각 단언한다.
  - rules-3 계약에 `creditTermId`를 넣은 상태
  - rules-4 계약의 `paymentDueDay`를 +1 한 상태
  - rules-4 계약의 `saleAmountMinor`를 +1 한 상태

  rules-4 R0P/R1에서 환전을 한 뒤 불변식이 깨끗한지도 단언한다(operations-invariants.ts:87).
- **E7 (8절 신규 변형):** "새 불변식 검사를 지움 → E6 시험 실패".
- **E8 (4.2-1, 108행):** "새 칸 일곱은 모두 있거나 모두 없다" → "`credit_terms`·`credit_limit_unit_minor`·`credit_limits`·`collections.carry_bp_per_day`·`recovery_bp` 다섯은 모두 있거나 모두 없다. 모두 있으면 grades 모든 행에 `p_default_bp`(0~10000)가 있고, 없으면 어느 행에도 없다".
- **E9 (7절 시험 6):** "save.ts:106(모르는 판본)"과 "save.ts:107" → 둘 다 "save.ts:107의 거절". 그리고 가르는 기준을 적는다. "옛 빌드는 `known`이 거짓이라 거절된다. 새 빌드는 `known`이 참이고 판본이 달라 거절되며, 문장에 '이 시나리오의 규칙은 M2a-rules-3이며'가 들어간다."
- **E10 (9절 2, 232행):** "새 시험 파일 A" → 세 조건으로 바꾼다.
  - `git diff --name-status <BASE> -- 'src/**/*.test.ts' 'tools/*.test.mjs' tests/golden`은 빈 출력이다.
  - `git diff --numstat <BASE> -- tools/test_validate_data.py`의 삭제 수가 0이다.
  - `git status --porcelain --untracked-files=all`의 `??` 줄은 새 시험 파일과 결과 보고뿐이다.
- **E11 (4.3, 142행 / 60행):** "등급은 loadRiskProfile(id)…에서 읽는다" → "creditTermCheck의 등급은 `config.operations.risk.profile.collections.byCounterparty`에서 읽는다(엔진은 content를 부르지 않는다)".

- **E12 (5.2, 156행):** 한 문장을 더한다. "acceptTrade는 오퍼 확인(offerDef·offerOpen) 바로 뒤, 수량·자금 검사보다 먼저 creditTermCheck를 부르고, 그 reasonKo를 그대로 돌려준다."
- **E13 (7절 시험 4, 204행 / 8절):** 사례 하나를 더한다. "손으로 만든 고정물(계약은 IN_PROGRESS, 청구서는 PAID)에서 노출액에서 빠진다." 변형 하나도 더한다. "청구서 상태 조건 지움 → 시험 4 실패."
